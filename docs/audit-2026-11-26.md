# Nest: аудит требований и кода — 26.11.2026

База: `main`, `93619f1`, Nest `0.1.3`, Windows, Node `24.19.0`, pnpm `12.18.0`. Аудит покрывает основной путь: проект → worktree → PTY и восстановление → Git/diff → комментарии → обновления. Сверка с [продуктовыми FR/NFR](product.md#L313-L360), [MVP DoD](roadmap.md#L276-L288), [архитектурой](architecture.md), [совместимостью CLI](harness-compat.md) и [поставкой](release.md). Код приложения не изменён. Вложенный untracked `flatworm/` не включён в аудит; не менять и не удалять его.

## С чего начать

- **Критично** — сначала исправить потерю управляемого состояния и неверное восстановление: **A1–A3**. Можно начинать с A1, не дожидаясь продуктовых решений.
- **Высоко** — видимые поломки основных сценариев: **A4–A10**. Исправлять отдельными изменениями с регрессионными тестами.
- **Средне** — остальные дефекты и пробелы: решать после A1–A10 или в рамках связанного изменения. Приоритеты аудита не заменяют продуктовые P0/P1.
- Если не указано «воспроизведено», вывод сделан по коду; критерии ниже — предлагаемые проверки, а не результаты прогона.

## Дефекты и критерии исправления

### A1 · Критично · Ошибка `git worktree remove` превращается в успешное удаление задачи (FR-02, NFR-08)

[TaskService.remove](../packages/core/src/services/tasks.ts#L157-L199) подавляет любую ошибку Git, пробует `prune` и безусловно удаляет строку задачи. SQLite каскадно удаляет сессии и комментарии ([схема](../packages/core/src/db/migrations.ts#L18-L58)). Worktree может остаться на диске, а пользователь потеряет вкладки и заметки; UI не получает ошибку и не предлагает повтор ([обработчик](../apps/desktop/src/renderer/src/App.tsx#L402-L447)). Ошибка `git status` также не означает «чисто».

**Критерий:** в тестовом репозитории блокировать чистый worktree штатной командой `git worktree lock` и вызвать обычное удаление: ожидаются структурированная ошибка, существующий путь и сохранённые task/session/comment. Подтверждать очистку записи отсутствующего workspace отдельно, после проверки регистрации Git. Только после успешного удаления (или подтверждённого отсутствия) чистить БД; не выполнять глобальный `prune` как замену проверке. Ветку сохранять по умолчанию, main checkout никогда не удалять.

### A2 · Критично · Удаление проекта оставляет живые PTY без вкладок (FR-01, FR-04, NFR-08)

Диалог обещает сохранить worktree на диске ([App](../apps/desktop/src/renderer/src/App.tsx#L343-L349)). IPC вызывает прямой [DELETE проекта](../packages/core/src/services/projects.ts#L110-L113), каскад убирает метаданные, но остановка PTY подключена только к [удалению задачи](../packages/core/src/index.ts#L60-L65). Процесс может продолжать работу, и UI уже не может им управлять. Worktree после повторного добавления проекта не появятся автоматически: регистрация создаёт только main checkout ([ProjectService.add](../packages/core/src/services/projects.ts#L78-L107)).

**Критерий:** удалить проект с работающими FakeHarness в main checkout и worktree; проверить подтверждённую остановку процессов, отсутствие последующих событий, сохранность обоих checkout на диске и отсутствие строк в БД. Если остановка не подтверждена — не сообщать об успехе. Уточнить в диалоге, что будет с историей и комментариями; импорт оставшихся worktree — отдельное продуктовое решение.

### A3 · Критично · `Resume exact` может открыть чужую беседу (FR-11/17)

[Discovery](../packages/core/src/harness/discovery.ts#L8-L15) принимает кандидатов за 15 секунд **до** старта. Для OpenCode идентификация — по `cwd` и времени ([выбор кандидата](../packages/core/src/harness/discovery.ts#L111-L130)). [SessionService](../packages/core/src/services/sessions.ts#L460-L489) закрепляет первое совпадение и [сохраняет `exact`](../packages/core/src/services/sessions.ts#L512-L523). **Воспроизведено на заглушке адаптера:** беседа другой вкладки, созданная на секунду раньше, возвращается при `includeUpdated:false`. При параллельных вкладках даже строгий timestamp не доказывает принадлежность. Документация [признаёт неоднозначность](harness-compat.md#L46-L57), но UI обещает exact и Nest может применить его при автозапуске.

**Критерий:** два процесса одного CLI в одном `cwd`, уже существующая беседа, отложенное создание новой и рестарт: один id не назначается нескольким вкладкам, старый id не захватывается новой вкладкой. Предпочесть идентификатор, полученный от конкретного запуска; при неоднозначном совпадении не ставить `exact` и не подменять беседу молча через автоматический latest. Отдельно определить судьбу уже сохранённых эвристических id.

### A4 · Высоко · Стыковка истории и live-вывода дублирует/переставляет данные PTY (FR-05/11)

[TerminalPane](../apps/desktop/src/renderer/src/components/TerminalPane.tsx#L632-L655) пишет live chunk сразу в xterm и отдельно запрашивает полную историю. Core [сначала добавляет chunk в буфер, затем шлёт его](../packages/core/src/services/sessions.ts#L249-L265); [RPC возвращает тот же буфер](../packages/core/src/services/sessions.ts#L385-L391). На reload/LRU один и тот же chunk может быть в обеих ветках, старые данные проигрываются после новых. Это влияет и на ANSI-состояние, а не только на дубли текста.

**Критерий:** snapshot с монотонной позицией потока + буферизация live до replay; применять только данные после позиции и в исходном порядке, не писать в размонтированный xterm. Тест с FakeHarness и пронумерованным потоком, намеренно перекрывающим snapshot, проверяет точное содержимое и порядок после reload и LRU-remount.

### A5 · Высоко · Git diff путает данные hunk с заголовками (FR-08/16)

В [парсере](../packages/core/src/git/diff.ts#L75-L119) проверки `---`/`+++` идут до чтения строк hunk. **Воспроизведено на фикстуре парсера:** при git-строках `--- before` и `+++ after` изменённые строки теряются, имя становится `after`, следующая строка привязывается к неверному номеру. Отдельно воспроизведено: бинарный diff с Git-quoted кириллическим путём возвращает пустой список; по той же ветке обработки могут теряться mode-only изменения ([разбор пути](../packages/core/src/git/diff.ts#L12-L42)).

**Критерий:** читать заголовки только вне hunk, покрыть реальные diff-фикстуры: строки, похожие на заголовки, кириллица/пробелы, binary/mode-only, rename. Проверять путь, тип, счётчики и номера строк для комментариев. Не подменять корректный Git-вывод пустым состоянием панели.

### A6 · Высоко · Diff не показывает staged и не даёт заявленных действий (FR-08, §5.4)

[DiffPanel](../apps/desktop/src/renderer/src/components/DiffPanel.tsx#L90-L105) зовёт `git.diff({taskId})`, а [GitService](../packages/core/src/services/git.ts#L52-L76) по умолчанию читает unstaged. После stage панель может сказать [«No changes to review»](../apps/desktop/src/renderer/src/components/DiffPanel.tsx#L427-L434), хотя индекс полон. Нет stage/unstage прямо в Diff и просмотра patch против base; Compare даёт отдельную сводку, не заменяющую режим ревью.

**Критерий:** при staged-only, unstaged-only и частично staged файле показывать явно выбранную сторону, дать stage/unstage без ухода из Diff. Для base согласовать, сравнивается ли текущий workspace (включая индекс) или только commits; состояние просмотрщика и источник якорей должны соответствовать выбранному режиму, а не всегда `HEAD → workspace`.

### A7 · Высоко · Сохранённые заметки исчезают из интерфейса (FR-16)

[Core re-anchor](../packages/core/src/services/comments.ts#L64-L82) правильно считает заметку не stale, если текст ещё существует в файле. Но [DiffPanel](../apps/desktop/src/renderer/src/components/DiffPanel.tsx#L557-L636) рисует только совпавшие видимые строки и stale fallback. Если hunk ушёл из текущего diff (stage, commit, другой контекст), заметка может быть в БД, но её нельзя открыть, отправить или resolve.

**Критерий:** дать область для заметок вне видимого patch, отдельно от `stale`. UI-тест: создать заметку → stage/commit → перезапустить Nest → найти заметку и отправить в FakeHarness. В том же проходе уточнить требования к редактированию, пакетной отправке и сценарию без живой сессии ([§5.4](product.md#L174-L183)); проверить поведение многострочного ввода на CLI — [текущая реализация](../packages/core/src/services/sessions.ts#L319-L323) всегда посылает bracketed paste и Enter, без заявленного fallback.

### A8 · Высоко · Crash теряет текущую историю и нет регулирования потока PTY (FR-05/11, NFR-02/03)

[onData](../packages/core/src/services/sessions.ts#L249-L265) копит хвост только в RAM и делает IPC на каждый chunk. Запись в БД происходит при [exit](../packages/core/src/services/sessions.ts#L267-L298) или [штатном shutdown](../packages/core/src/services/sessions.ts#L421-L435). После аварии сессия [помечается для resume](../packages/core/src/services/sessions.ts#L393-L419), но вывод с последней записи потерян. Срез raw ANSI также не эквивалентен snapshot экрана. В архитектуре описаны [batching, backpressure и snapshot](architecture.md#L364-L399), в этом пути их нет.

**Критерий:** сначала согласовать окно допустимой потери при аварии; периодически сохранять ограниченный объём данных и измерить накладные расходы. Ввести batching/ограничение очереди с учётом скрытых и вытесненных xterm, совместно с A4. Тесты: принудительно закрыть **тестовый** Electron до нормального exit, восстановить подтверждённый объём; нагрузочный FakeHarness с 10 сессиями и измерением памяти/задержки. Не считать уже прошедший graceful restart подтверждением crash recovery.

### A9 · Высоко · Первый push задачи с базой `origin/main` ломается (FR-02/09)

[Создание](../packages/core/src/services/tasks.ts#L89-L115) передаёт remote-tracking base в `git worktree add -b` без `--no-track`. При типичных настройках новая `nest/<slug>` наследует upstream `origin/main`. [Push](../packages/core/src/services/git.ts#L118-L135) тогда запускает обычный `git push`; с `push.default=simple` разные имена веток дают отказ, а не публикацию task branch.

**Критерий:** локальный bare `origin`, `branch.autoSetupMerge=true`, `push.default=simple`; создать задачу от `origin/main`, закоммитить и впервые запушить. На origin появляется `nest/<slug>`, `main` не меняется. Явно разделить base и upstream (например, `--no-track` для новых задач); для существующих с неправильным upstream показать безопасный способ публикации, не переписывая пользовательский upstream без согласия.

### A10 · Высоко · Discard/Unstage переименования учитывают только новый путь (FR-07/08, NFR-08)

[Разбор статуса](../packages/core/src/services/git.ts#L558-L578) пропускает оригинальный путь rename; [панель](../apps/desktop/src/renderer/src/components/GitPanel.tsx#L118-L125) передаёт только destination. [Discard](../packages/core/src/services/git.ts#L405-L433) восстанавливает его из `HEAD`, где этого пути нет: новый файл исчезает, а staged-удаление исходного остаётся. [Unstage](../packages/core/src/services/git.ts#L84-L91) имеет ту же проблему с неполным pathset.

**Критерий:** после `git mv` в тестовом репозитории Discard восстанавливает старое имя и оставляет чистый статус; Unstage снимает обе части с индекса и не удаляет файл из workspace. Перед подтверждением показывать `old → new`; учитывать rename отдельно от copy.

## Требования, которые надо уточнить или довести до конца

- **FR-02, §5.2 — создание задачи.** [New Task](../apps/desktop/src/renderer/src/components/NewTaskDialog.tsx#L107-L160) не показывает конкретный путь/ветку, не выбирает harness и не выполняет `Create & start`. Прогресс только в модалке, кнопка `Cancel` закрывает её, но не отменяет RPC; завершение [переключает фокус на новую задачу](../apps/desktop/src/renderer/src/App.tsx#L357-L397), даже если пользователь уже работает в другой. Согласовать отдельные `Create task` / `Create & start`, прогресс по ID операции в дереве и семантику `Close` vs `Cancel`. При сбое запуска сохранять созданную задачу и давать повтор запуска без второго worktree. E2E должен создавать задачу через UI, включая main checkout, а не через bridge.
- **FR-01 — base ref.** [Регистрация](../packages/core/src/services/projects.ts#L56-L87) определяет текущую ветку, но не хранит default base; [без явного ввода берётся текущая ветка](../packages/core/src/services/tasks.ts#L208-L225). Решить, требуется ли default base (`origin/HEAD` с fallback) или лучше явно оставить current branch; показывать эффективную базу до создания, проверить offline и remote-less. Не добавлять обязательный сетевой шаг.
- **FR-03/06/10/14 — мониторинг.** [SessionStatus](../packages/shared/src/schemas.ts#L154-L172) не имеет `needs_input`; [Activity](../apps/desktop/src/renderer/src/activity.ts#L35-L47) считает тихого фонового агента «Waiting for you», хотя PTY может просто молчать во время работы. Без hook честнее показывать `Idle`; уточнить, должен ли отдельный список покрывать все живые PTY (в т. ч. shell), и добавить `Other running` либо снять требование: [правая панель](../apps/desktop/src/renderer/src/components/RightPanel.tsx#L135-L146) даёт только сессии выбранной задачи. Разделить стабильный generic PTY и точный статус только для профилей с проверенной интеграцией.
- **FR-09, §5.5 и §5.8 — Git UX.** Отдельные [Commit и Push](../apps/desktop/src/renderer/src/components/GitPanel.tsx#L129-L172) есть; заявлены также `Commit & push`, ссылка на remote и явная маркировка общего checkout в Git-панели. Если объединённую кнопку сохраняем в требованиях, при push failure сообщать, что локальный commit уже создан; повтор должен делать только push.
- **FR-12, §6.7, NFR-04/06 — настройки и сеть.** Worktree root доступен через [переменную окружения](../apps/desktop/src/main/index.ts#L31-L36), но отсутствует в [схеме настроек](../packages/shared/src/schemas.ts#L99-L125); тема терминала уже есть, целиком тему приложения не обещать без решения. По обновлениям [product](product.md#L301-L311) говорит «пустое значение отключает», а [реализация](../apps/desktop/src/main/updateFeed.ts#L5-L11) и [runbook](release.md#L94-L111) — «пустое значение включает встроенный GitHub feed». [Privacy](privacy.md#L22-L29) описывает запросы как условные. Согласовать default, opt-out и приоритет override; если оставляем default GitHub, добавить видимый выключатель и зафиксировать политику. Автоматическое копирование `.env` в каждый worktree ([реализация](../packages/core/src/services/setup.ts#L22-L45)) также стоит сделать явным выбором: копии ключей могут оказаться в workspace, если файл не игнорируется.
